# 06 敏捷需求：Epic / User Story / Acceptance Criteria

## 本章目标

理解传统 SRS 与敏捷 User Story 并不冲突。

敏捷不等于“不写需求”，而是把需求分解成适合迭代交付和持续沟通的工作项。

## 一、层级

常见层级：

**Business Goal → Initiative → Epic → Feature → User Story → Task / Test**

不同组织名称不同，重点是建立层次。

## 二、User Story

经典格式：

> 作为 [角色]，我希望 [能力]，以便 [价值]。

例：

> 作为患者，我希望取消尚未开始的预约，以便在计划改变时释放号源。

User Story 的作用是表达“谁、要什么、为什么”，不是代替所有规格细节。

## 三、3C 原则

User Story 常用：

- **Card**：简短记录
- **Conversation**：团队讨论
- **Confirmation**：明确验收

Spec Engineer 的价值主要在 Conversation 与 Confirmation。

## 四、Acceptance Criteria

验收标准必须具体。

可以采用 Given / When / Then：

### AC-01 正常取消

Given 患者已登录  
And 预约属于该患者  
And 状态为 BOOKED  
And 距开始时间 ≥ 2 小时  
When 患者提交取消  
Then 系统将预约状态更新为 CANCELLED  
And 释放号源

### AC-02 超过取消窗口

Given 距预约开始不足 2 小时  
When 患者提交取消  
Then 系统拒绝操作  
And 返回明确错误提示

## 五、INVEST

高质量 User Story 常用 INVEST 检查：

- Independent
- Negotiable
- Valuable
- Estimable
- Small
- Testable

不应机械套用，重点是发现过大、依赖过强和不可测试的 Story。

## 六、Epic 如何拆

不要只按“前端/后端”拆。

更推荐按用户价值或场景：

大 Epic：预约管理

拆为：

- 查看医生
- 查看可用号源
- 创建预约
- 查看我的预约
- 取消预约
- 改期
- 管理员代预约

每个 Story 都尽量能独立产生可验证价值。

## 七、Story 不够时怎么办

复杂系统中，单独 User Story 往往不够。

可以关联：

- Business Rule
- API Spec
- Data Dictionary
- State Machine
- UX Prototype
- Security Requirement
- NFR
- Test Cases

这正是“轻量工作项 + 稳定工程文档”的组合。

## 八、Backlog Refinement

Spec Engineer 在 Refinement 中重点回答：

- Story 是否过大？
- 是否有隐藏依赖？
- 业务规则是否明确？
- 异常是否覆盖？
- 数据是否明确？
- 权限是否明确？
- 是否具备 Acceptance Criteria？
- QA 能否开始写测试？

## 九、Definition of Done

DoD 与 Acceptance Criteria 不相同。

Acceptance Criteria：这个 Story 的业务行为。

Definition of Done：团队对“完成”的公共标准。

例如：

- 代码合并
- 单元测试通过
- API 文档更新
- 安全扫描通过
- Acceptance Test 通过
- Release Note 更新

## 十、练习

把“预约管理”拆成：

- 1 个 Epic
- 至少 6 个 User Stories
- 每个 Story 至少 3 个 Acceptance Criteria
- 至少 1 个异常 AC
