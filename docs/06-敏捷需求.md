# 06 敏捷需求：Epic、User Story、Acceptance Criteria 与 Backlog Refinement

> 本章目标：理解敏捷开发不是“少写文档”，而是让需求以可迭代、可验证、可持续讨论的方式流动。

---

# 1. 敏捷需求和 SRS 不冲突

大型长期约束适合稳定文档：
- Glossary
- Business Rules
- API
- Data
- Permissions
- NFR

迭代交付适合 Backlog：
- Epic
- Story
- Bug
- Task

推荐组合：

```
Stable Engineering Docs
        +
Iteration Backlog
```

---

# 2. 层级

常见：

```
Business Goal
  ↓
Initiative
  ↓
Epic
  ↓
Feature
  ↓
User Story
  ↓
Task
```

不同团队名称会变，但要防止所有需求都挤在同一层。

---

# 3. Epic

Epic 是较大的用户价值或业务能力。

例：

> 在线预约管理

可能拆成：
- 查询医生
- 查询 Slot
- 创建预约
- 查看预约
- 取消预约
- 改期

不要拆成：
- 前端 Epic
- 后端 Epic
- DB Epic

因为这不是用户价值维度。

---

# 4. User Story

经典格式：

> 作为 [角色]，我希望 [能力]，以便 [价值]。

例：

> 作为患者，我希望查看医生可预约时间，以便选择适合自己的时间。

User Story 不是完整 Spec。

它只回答：
- Who
- What
- Why

剩余细节通过：
- Conversation
- Acceptance Criteria
- Business Rule
- API
- Data
- Model

补齐。

---

# 5. 3C

Atlassian 等敏捷资料常强调 Story 是讨论的起点，而非全部文档。

可以用 3C：

- Card
- Conversation
- Confirmation

### Card
短需求描述。

### Conversation
Product/Spec/Dev/QA 讨论。

### Confirmation
Acceptance Criteria / Testable Result。

---

# 6. Acceptance Criteria

AC 回答：

> 什么情况下这个 Story 可以被验收？

使用 Given / When / Then：

```
Given 患者已登录
And Slot 状态为 AVAILABLE
When 患者提交预约
Then 系统创建 BOOKED Appointment
And Slot 不再可预约
```

---

# 7. AC 不等于 Test Case

AC：
- 业务验收行为

Test Case：
- 更详细测试输入、步骤、数据、预期

一个 AC 通常会生成多个 Test Case。

---

# 8. INVEST

常见 Story 检查：

- Independent
- Negotiable
- Valuable
- Estimable
- Small
- Testable

关键不是背英文，而是问：

- 是否可以独立交付？
- 是否保留讨论空间？
- 是否有用户价值？
- 是否能估算？
- 是否太大？
- 是否可测试？

---

# 9. Story 太大怎么拆

可以按：

### Workflow
创建 → 修改 → 删除

### Happy / Exception
先正常，再复杂异常

### Rule
普通用户 / 管理员

### Data
基础字段 / 高级字段

### CRUD
Create / Read / Update / Delete

### Business Value
最小可用闭环

但不要为了“小”而破坏端到端价值。

---

# 10. Example Mapping

一个很实用的 Refinement 技巧：

```
Story
 ↓
Rules
 ↓
Examples
 ↓
Questions
```

例：

Story：
> 患者取消预约。

Rules：
- 只能自己的
- BOOKED
- >=2h

Examples：
- 3h → 成功
- 2h → 成功
- 1h59m → 失败

Questions：
- Admin 是否受 2h 限制？

Example 能迅速暴露模糊。

---

# 11. Backlog Refinement

Spec Engineer 在 Refinement 中检查：

- Goal 清楚？
- Story 是否过大？
- Business Rule？
- Dependencies？
- Data？
- Permission？
- Failure？
- Boundary？
- AC？
- NFR？
- Open Question？

如果关键问题没解决，不应该为了 Sprint 节奏假装 Ready。

---

# 12. Definition of Ready

团队可约定：

- Story 描述清楚
- AC 完成
- 依赖确认
- UX 可用
- API/Data 已确认
- 无阻塞性 Open Question
- 可估算

DoR 不是行业统一标准，应团队定义。

---

# 13. Definition of Done

DoD 是“所有 Story 都适用的完成标准”。

例：
- code merged
- unit test pass
- security scan pass
- API docs updated
- acceptance test pass
- monitoring added

它和 AC 不同：
- AC = 此 Story 特定业务要求
- DoD = 团队公共完成标准

---

# 14. Story 与 Requirement 的追踪

示例：

```
STORY APPT-101
  ↳ Requirement APPT-001
  ↳ Requirement APPT-002
  ↳ BR-003
  ↳ API POST /appointments
  ↳ Test TC-001~TC-008
```

不要假设 Story 和 Requirement 必须一一对应。

---

# 15. 敏捷项目中的变更

敏捷不等于随便改。

已进入 Sprint 的 Requirement 变化时仍需：
- 记录原因
- 评估影响
- 更新 AC
- 更新 Test
- 与团队确认

---

# 16. 完整案例

Epic：

> EPIC-APPT 在线预约

Story：

> APPT-101 作为患者，我希望创建预约，以便获得指定时间的医生服务。

Rules：
- patient = current user
- slot available
- one active appointment per slot

AC：

### AC1
AVAILABLE → 201 + BOOKED

### AC2
already booked → 409

### AC3
other patientId → 403

### AC4
concurrent same slot → exactly one success

对应：
- API
- DB
- Test
- NFR

---

# 17. 本章练习

设计“企业请假”：

Epic：
请假管理

至少拆：
- 提交
- 修改
- 撤回
- 审批
- 拒绝
- 查询
- 余额

每个 Story：
- 1 User Story
- 3 Rules
- 4 AC
- 2 Open Questions
