# 03 需求获取与利益相关者分析

## 本章目标

学完后你应该能：

- 找到真正的需求来源，而不是只记录“客户说的话”
- 识别利益相关者并判断影响力、职责和冲突
- 设计访谈问题、观察场景和需求研讨会
- 区分事实、假设、意见和待确认项
- 把原始材料整理为结构化需求

## 一、为什么需求获取最容易出问题

很多项目不是“开发错了”，而是一开始就没有把问题问清楚。

典型失败：

- 只访谈管理者，没有访谈实际操作人员
- 只问“你需要什么功能”，没有问“你现在怎么做”
- 用户描述的是旧系统按钮，而不是业务目标
- 没有识别法规、安全、运维等隐藏利益相关者
- 把“解决方案偏好”误当成“需求”

例：

用户说：“这里加一个导出 Excel 按钮。”

Spec Engineer 不应立刻记录成需求，而要继续问：

- 为什么需要导出？
- 导出后做什么？
- 谁使用？
- 导出哪些字段？
- 是否可以由报表功能替代？
- 是否涉及敏感数据？

## 二、Stakeholder（利益相关者）

利益相关者是任何会：

- 使用系统
- 影响系统
- 被系统影响
- 批准系统
- 运维系统
- 审计系统

的人或组织。

医疗预约 SaaS 可能包括：

- 患者
- 医生
- 护士
- 前台
- 医院管理员
- IT 运维
- 信息安全人员
- 财务人员
- 法务/合规
- 第三方短信服务商

## 三、利益相关者分析表

建议至少记录：

| Stakeholder | 目标 | 关注点 | 影响力 | 参与方式 |
|---|---|---|---|---|
| 患者 | 快速预约 | 易用、可取消 | 中 | 访谈/可用性测试 |
| 医生 | 避免冲突 | 排班准确 | 高 | Workshop |
| 前台 | 快速代预约 | 搜索效率 | 高 | 现场观察 |
| IT | 稳定运行 | 安全、监控 | 高 | 技术评审 |

## 四、需求获取方法

### 1. Interview（访谈）

适合探索个人经验、隐性规则和痛点。

避免只问封闭问题。

差：

“你需要预约提醒吗？”

好：

“患者错过预约通常是什么原因？现在如何提醒？”

### 2. Observation（观察）

用户自己未必能准确描述日常工作。

观察重点：

- 操作顺序
- 临时绕过方式
- Excel/纸张等辅助工具
- 重复录入
- 等待
- 手工核对
- 非正式沟通

### 3. Workshop（研讨会）

适合多个部门共同澄清：

- 流程
- 边界
- 优先级
- 冲突
- 业务规则

Spec Engineer 应记录决策和未决事项。

### 4. Document Analysis（文档分析）

资料可能包括：

- SOP
- 法规
- 合同
- 用户手册
- 历史需求
- 缺陷单
- API 文档
- 数据字典

### 5. Prototype（原型）

适合验证交互和理解是否一致。

原型不是需求本身，它是澄清需求的一种手段。

## 五、访谈问题模板

### 背景

- 你的角色是什么？
- 日常工作目标是什么？
- 哪些任务最频繁？

### 当前流程

- 从什么事件开始？
- 第一步做什么？
- 接下来呢？
- 什么情况下流程不同？

### 数据

- 需要输入什么信息？
- 信息从哪里来？
- 哪些字段必填？
- 如何判断数据正确？

### 异常

- 最常见失败是什么？
- 数据缺失怎么办？
- 两个人同时操作怎么办？
- 第三方服务不可用怎么办？

### 权限

- 谁可以查看？
- 谁可以修改？
- 谁可以删除？
- 是否需要审批？

### 质量

- 最慢可以接受多慢？
- 哪些操作绝对不能丢数据？
- 哪些操作必须留痕？

## 六、事实、假设与待确认项

需求研讨中一定要标记：

- **Fact**：已经有证据确认
- **Assumption**：当前推测
- **Decision**：已批准决定
- **Open Question**：未决问题
- **Risk**：可能影响项目

不要把 Assumption 写成 Requirement。

## 七、需求获取输出

一次有效需求获取不应只有会议纪要。

应逐步产生：

- Stakeholder List
- Glossary
- As-Is Process
- Pain Points
- Business Rules
- Candidate Requirements
- Open Questions
- Decision Log

## 八、练习

围绕“患者取消预约”做一次模拟访谈。

至少输出：

1. 10 个访谈问题
2. 3 个利益相关者
3. 5 条业务规则
4. 3 个异常场景
5. 3 个待确认问题
6. 5 条候选需求
