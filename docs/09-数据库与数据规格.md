# 09 数据库与数据规格

## 本章目标

你不需要成为 DBA，但必须能把业务对象转成数据规格并读懂 SQL。

## 一、核心概念

- Table 表
- Row 行
- Column 列
- Primary Key 主键
- Foreign Key 外键
- Unique Constraint 唯一约束
- Index 索引
- Transaction 事务
- NULL
- Data Type 数据类型

## 二、从业务对象到实体

医疗预约系统常见实体：
- Patient
- Doctor
- Schedule
- Slot
- Appointment
- User
- Role
- AuditLog

不要一开始就围绕页面设计表，而要围绕业务对象和关系。

## 三、数据字典

每个关键字段应定义：

| 字段 | 类型 | 可空 | 说明 | 规则 |
|---|---|---|---|---|
| appointment_id | UUID | 否 | 预约唯一ID | PK |
| patient_id | UUID | 否 | 患者ID | FK |
| slot_id | UUID | 否 | 号源ID | FK |
| status | varchar | 否 | 状态 | 枚举 |
| created_at | datetime | 否 | 创建时间 | UTC |

## 四、主键与业务编号

数据库主键不一定等于用户看到的业务编号。

例如：
- internal id: UUID
- appointment_no: AP202609250001

Spec 要区分。

## 五、NULL

NULL 不等于空字符串，也不等于 0。

每个字段都问：
- 是否允许缺失？
- 缺失代表什么？
- 默认值是什么？

## 六、关系

常见：
- 一对一
- 一对多
- 多对多

例如：
一个医生有多个排班；
一个患者有多个预约。

## 七、规范化的基本思想

不要把大量重复信息塞进一个表。

目标：
- 减少冗余
- 避免更新不一致
- 明确实体关系

但商业系统也可能为性能做适当反规范化，这属于架构权衡。

## 八、数据生命周期

Spec 需要考虑：
- 创建
- 修改
- 归档
- 删除
- 保留期限
- 恢复
- 审计

尤其医疗、金融等领域不能简单用“DELETE”理解业务删除。

## 九、敏感数据

识别：
- 身份信息
- 联系方式
- 医疗信息
- 凭证
- Token

并定义：
- 谁能看
- 谁能改
- 是否脱敏
- 是否加密
- 是否记录访问

## 十、SQL 最低要求

至少会：
- SELECT
- WHERE
- JOIN
- GROUP BY
- ORDER BY
- INSERT
- UPDATE
- 基本事务概念

Spec Engineer 需要用 SQL 验证数据理解、分析现有系统。

为以下实体写数据字典：

并定义：
- PK
