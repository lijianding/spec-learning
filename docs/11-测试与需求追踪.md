# 11 测试设计与需求可追溯性

## 本章目标

Spec 写完不等于结束。必须能够证明实现符合 Spec。

## 一、Test Basis

测试设计的依据可以来自：
- Requirement
- User Story
- Acceptance Criteria
- Use Case
- API Spec
- Business Rule
- State Diagram
- NFR

如果没有明确 Test Basis，测试很容易变成“凭经验点页面”。

## 二、从需求生成测试条件

需求：
> 当预约状态为 BOOKED 且距离开始时间不少于 2 小时时，患者可以取消。

测试条件至少包括：
- BOOKED + >2h
- BOOKED + =2h
- BOOKED + <2h
- CANCELLED
- COMPLETED
- 别人的预约
- 未登录
- 重复取消
- 并发取消

## 三、边界值

边界最容易出错。

规则 ≥ 2 小时：
- 1h59m59s
- 2h00m00s
- 2h00m01s

## 四、等价类

把大量输入划成代表性集合。

年龄允许 0~120：
- <0
- 0~120
- >120
- 非数字
- null

## 五、状态转换测试

如果对象有状态机，就必须检查：
- 允许转换
- 禁止转换
- 每条转换的权限
- 重复操作

## 六、Traceability Matrix

| Requirement | Design/API | Test Case | Result |
|---|---|---|---|
| APPT-001 | POST /appointments | TC-001, TC-002 | Pass |
| APPT-002 | Auth Policy | TC-003 | Pass |

价值：
- 知道哪些需求没测试
- 变更时找到受影响测试
- 缺陷时追溯原需求
- 审核时提供证据

## 七、正向和反向追踪

正向：
Requirement → Design → Code/Task → Test

反向：
Test / Feature → 它为什么存在？对应哪个 Requirement？

两边都需要。

## 八、缺陷反馈到 Spec

发现 Bug 时要先判断：
1. 实现不符合 Spec？
2. Spec 本身错误？
3. Spec 缺失？
4. 不同文档冲突？

不要把所有问题都归类为代码 Bug。

## 九、测试层次

理解即可：
- Unit Test
- Integration Test
- System Test
- End-to-End Test
- Acceptance Test

Spec Engineer 通常关注 System / Acceptance，但接口和规则也要支持更低层验证。

## 十、练习

选 10 条自己的 Requirement：
- 每条写至少 2 个 Test Case
- 建追踪矩阵
- 检查有没有 Requirement 没测试
- 检查有没有 Test 没有来源
