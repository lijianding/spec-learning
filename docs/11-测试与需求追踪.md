# 11 测试设计与需求可追溯性：证明 Spec 被正确实现

> 本章目标：让你从“写完 Requirement”进阶到“能够证明 Requirement 被实现”。

## 1. Verification 与 Validation

### Verification
> 我们是否按规格正确构建？

### Validation
> 这个规格是否真正解决需要解决的问题？

例如：
- 系统严格按“1 小时取消窗口”开发，Verification 可能通过
- 但真实业务需要“2 小时”，Validation 仍然失败

Spec Engineer 两者都要关心。

## 2. Test Basis

测试依据可以来自：
- Requirement
- User Story
- Acceptance Criteria
- Use Case
- State Model
- API Spec
- Business Rule
- NFR

测试不是随机点击。

## 3. Test Condition

Requirement：

> 只有 BOOKED Appointment 可以被 Patient 取消。

Test Conditions：
- BOOKED
- CANCELLED
- CHECKED_IN
- COMPLETED
- NO_SHOW

## 4. Test Case 基本结构

```
ID
Related Requirement
Precondition
Test Data
Steps
Expected Result
Postcondition
```

例：

```
TC-CAN-001
Req: APPT-CAN-003

Precondition:
Patient owns a BOOKED appointment.
Start time = now + 2h.

Step:
POST /appointments/{id}/cancel

Expected:
success
status=CANCELLED
slot=AVAILABLE
audit event exists
```

## 5. Positive / Negative

Positive：
满足条件，应成功。

Negative：
违反规则，应失败。

不要只测 Happy Path。

## 6. Equivalence Partitioning

ISTQB Foundation 包含 Equivalence Partitioning。

思想：

> 把输入划分为预期行为相同的集合，每组选择代表值。

年龄规则 0~120：

- <0 invalid
- 0~120 valid
- >120 invalid
- null
- non-number

## 7. Boundary Value Analysis

边界最容易出 Bug。

取消规则 >=2h：

- 1:59:59
- 2:00:00
- 2:00:01

长度 1~50：

- 0
- 1
- 50
- 51

## 8. Decision Table

适合多个条件组合。

| Own | BOOKED | >=2h | Result |
|---|---|---|---|
| Y | Y | Y | Allow |
| N | Y | Y | Deny |
| Y | N | Y | Deny |
| Y | Y | N | Deny |

规则多时，Decision Table 比自然语言更容易发现遗漏组合。

## 9. State Transition Testing

根据状态机：

```text
BOOKED → CANCELLED
BOOKED → CHECKED_IN
BOOKED → NO_SHOW
CHECKED_IN → COMPLETED
```

测试：
- valid transitions
- invalid transitions
- repeated transition

例如：
`COMPLETED → CANCELLED` 应拒绝。

## 10. Use Case Testing

从：
- Main Flow
- Alternative Flow
- Exception Flow

派生测试。

每个关键分支都应有覆盖。

## 11. API Test

检查：
- status
- schema
- response body
- permission
- business code
- headers
- idempotency
- pagination

## 12. Authorization Test

每个对象级操作至少考虑：

- owner
- other user
- admin
- unauthenticated
- wrong tenant

## 13. Concurrency Test

两个用户同时抢最后一个 Slot。

Expected：
- exactly one success
- another conflict
- only one active Appointment

这类场景不能只靠普通 UI 手工点击充分证明。

## 14. NFR Test

Performance Requirement：
- load test

Reliability：
- failure/recovery test

Security：
- security verification

Backup：
- restore test

每类 NFR 都要对应验证方法。

## 15. Traceability Matrix

```text
Requirement → Design/API → Test → Result
```

示例：

| Req | API/Design | Test | Result |
|---|---|---|---|
| APPT-001 | POST /appointments | TC-001 | Pass |
| APPT-005 | transaction | TC-CONC-01 | Pass |
| SEC-001 | authz middleware | TC-SEC-01 | Pass |

## 16. 为什么追踪很重要

### Coverage
哪些 Requirement 没测试？

### Change Impact
Requirement 改了，哪些 Test 受影响？

### Defect
Bug 对应哪条 Requirement？

### Audit
能否证明需求被验证？

## 17. Forward Traceability

```text
Requirement
→ Design
→ Code/Task
→ Test
```

回答：

> 我们有没有把这个 Requirement 做完？

## 18. Backward Traceability

```text
Test/Feature
→ Requirement
→ Business Goal
```

回答：

> 这个功能为什么存在？

还能发现 Gold Plating：开发了没人要求的功能。

## 19. Coverage

一个简单指标：

```text
至少关联一个测试的 Requirement 数
÷
总 Requirement 数
```

但“有测试”不等于测试质量高。

还应检查：
- happy
- negative
- boundary
- permission
- state
- concurrency

## 20. Defect Triage

发现问题时先分类：

### Implementation Bug
Spec 正确，实现错误。

### Requirement Defect
Spec 本身写错。

### Missing Requirement
根本没有定义。

### Conflict
两个文档不一致。

### Environment
环境/配置问题。

不要所有问题都丢给 Developer。

## 21. Requirement Change

假设取消规则从：

```text
cancel >= 2h
```

改为：

```text
cancel >= 30m
```

影响可能包括：
- Requirement
- Acceptance Criteria
- Boundary Value Test
- API error
- UI message
- Help docs
- automated tests

Traceability 帮助你找到这些对象。

## 22. Test Evidence

高要求项目不能只写：

> “已经测过。”

应保存：
- Test Case
- Execution
- Result
- Build/Version
- Environment
- Evidence

## 23. AI 辅助测试

AI 可以：
- 从 Requirement 生成候选 Test
- 找边界
- 找异常
- 建 Decision Table

但必须检查：
- 是否凭空增加规则？
- 是否遗漏状态？
- 是否理解权限？
- 是否覆盖真实边界？

## 24. 本章练习

选择 10 条 Appointment Requirement：

每条至少生成：
- 1 positive
- 1 negative

其中：
- 3 条做 Boundary
- 2 条做 Decision Table
- 2 条做 State Transition
- 1 条做 Concurrency
- 2 条做 Authorization

最后建立 Traceability Matrix。
