# 02 需求工程基础

## 本章目标

掌握需求工程最核心的语言和方法，为后续所有章节打基础。

## 一、什么是需求工程

Requirements Engineering（需求工程）不是单纯“写需求文档”。

完整过程通常包括：

1. 识别需求来源
2. 获取需求
3. 分析需求
4. 记录需求
5. 验证需求
6. 协商冲突
7. 确定优先级
8. 管理版本与变更
9. 建立追踪关系

IREB CPRE Foundation 将需求工程基础能力概括为理解需求工程原则、工作产品、需求开发实践、过程配置和需求管理。

## 二、需求的来源

需求可能来自：

- 最终用户
- 客户
- 管理层
- 法规
- 合同
- 现有系统
- 第三方系统
- 运维团队
- 安全团队
- 数据团队
- 技术限制
- 历史缺陷
- 用户反馈

新手最常见错误是：只把“客户说的话”当作需求。

## 三、需求类型

### 业务需求

为什么要做。

### 用户需求

用户需要实现什么目标。

### 功能需求

系统必须提供哪些行为。

### 非功能需求

性能、安全、可靠性、兼容性、可维护性等质量要求。

### 约束

系统不能自由选择的条件。

例如：

- 必须部署在客户内网
- 必须使用 SQL Server
- 必须保留七年审计日志
- 必须对接已有 HIS 接口

### 业务规则

业务世界本身的规则。

例如：

“同一医生同一时间段只能存在一个有效预约。”

业务规则最好单独管理，而不是散落在几十条功能需求里。

## 四、一个需求应该具备什么质量

建议用以下八项检查：

### 1. 必要

如果删掉这条需求，业务目标是否受影响？

### 2. 明确

不同的人读完是否会得到相同理解？

避免：

“系统应快速显示结果。”

改为：

“在正常负载下，95% 的查询请求应在 300 ms 内返回。”

### 3. 单一

一条需求尽量只表达一个可验证行为。

避免：

“系统应创建预约并发短信并更新医生日程。”

应拆成多条需求。

### 4. 一致

不能与其他需求冲突。

### 5. 完整

前置条件、输入、输出、异常、边界是否说明？

### 6. 可实现

技术和成本上是否现实？

### 7. 可验证

测试人员能否设计明确测试？

### 8. 可追踪

能否知道它来自哪里，又影响哪些设计和测试？

## 五、使用“shall / 必须”表达系统义务

规范性需求应尽量采用固定句式：

“当……时，系统必须……”

例如：

“当预约时段状态为 AVAILABLE 且满足预约规则时，系统必须创建预约记录。”

这样比“支持预约功能”清晰得多。

## 六、需求 ID

每条可管理需求应有稳定 ID。

示例：

- AUTH-001
- PAT-001
- APPT-001
- SCH-001
- NFR-SEC-001
- NFR-PERF-001

ID 不应该随着标题小改动而变化。

## 七、需求属性

除了正文，建议记录：

| 属性 | 示例 |
|---|---|
| ID | APPT-001 |
| 标题 | 创建预约 |
| 类型 | Functional |
| 来源 | Patient Interview |
| 优先级 | Must |
| 状态 | Approved |
| Owner | Product |
| 版本 | 1.2 |
| 验证方式 | API + E2E Test |
| 关联用例 | UC-APPT-01 |

这就是需求管理系统背后的基本思想。

## 八、Baseline（基线）

当一组需求经过评审并正式用于开发后，可以建立 Baseline。

基线意味着：

“这是当前被批准用于实现和验证的版本。”

后续修改不能悄悄覆盖，而应形成 Change Request。

## 九、Change Request

变更至少回答：

1. 为什么要改？
2. 原需求是什么？
3. 新需求是什么？
4. 哪些模块受影响？
5. 哪些接口受影响？
6. 哪些数据受影响？
7. 哪些测试受影响？
8. 是否影响上线计划？
9. 谁批准？

## 十、本章练习

写出 10 条医疗预约 SaaS 需求，并逐条填写：

- ID
- 类型
- 来源
- 优先级
- 验证方式

然后检查是否满足：

- 单一
- 无歧义
- 可测试
- 可追踪

## 本章完成标准

当你看到一句“支持患者快速预约医生”时，不应直接把它交给开发，而应本能地追问：

- 谁？
- 在什么条件下？
- 输入是什么？
- 规则是什么？
- 成功结果是什么？
- 失败结果是什么？
- 边界是什么？
- 如何验证？
