# 02 需求工程基础：从“想法”到可验证需求

> 本章目标：建立 Requirements Engineering（需求工程）的完整框架。学完后，你应该能区分不同层级的需求、判断需求质量、建立需求属性、理解基线/变更/追踪，并能把模糊描述改写为候选 Requirement。

---

# 1. 什么是需求工程

需求工程不是“写需求文档”，而是一组贯穿软件生命周期的工程活动。

IREB CPRE Foundation 将需求工程覆盖为：

- 识别和分析利益相关者
- 获取需求（Elicitation）
- 对需求进行文档化
- 建模
- 验证（Validation）
- 协商冲突
- 管理需求
- 建立追踪
- 处理变更
- 根据项目情况调整需求工程过程

可以把它理解成：

```
真实问题
  ↓
需求来源
  ↓
获取与澄清
  ↓
分析与建模
  ↓
规格说明
  ↓
验证与评审
  ↓
批准/基线
  ↓
开发与测试
  ↓
变更与持续维护
```

重要：**Requirement 不是一句话，而是一个被管理、被验证、被追踪的工程对象。**

---

# 2. 需求从哪里来

新手常见误区：

> “客户说的就是需求。”

实际项目中，需求来源可能包括：

- 最终用户
- 客户
- 管理层
- 产品负责人
- 合同
- 法律法规
- 行业标准
- 安全政策
- 运维要求
- 已有系统
- 旧系统数据库
- API
- 报表
- Excel
- 缺陷
- 用户反馈
- 日志
- 第三方系统
- 技术限制

因此 Spec Engineer 要问的不只是：

> “用户想要什么？”

还要问：

> “有哪些约束即使用户没有主动说，也会决定系统必须怎样工作？”

---

# 3. 需求的常见层级

不同公司名称会不同，但可以使用以下四层理解。

## 3.1 Business Requirement

回答：

> 为什么做？

例：

```
BR-001
诊所希望将电话预约量降低 50%。
```

它描述业务结果，不描述页面或 API。

---

## 3.2 User Requirement

回答：

> 用户希望完成什么目标？

例：

```
UR-001
患者应能够在线查看医生可预约时间。
```

---

## 3.3 System / Software Requirement

回答：

> 系统必须表现成什么样？

例：

```
SLOT-001
当患者选择医生和日期时，系统必须返回该医生在该日期仍可预约的时间段。
```

---

## 3.4 Technical Specification

回答：

> 软件接口、数据、错误行为等具体契约是什么？

例：

```
GET /api/v1/doctors/{doctorId}/slots?date=2026-10-01

200: 返回可预约 Slot
400: 日期格式错误
404: doctorId 不存在
```

---

# 4. 功能需求、非功能需求与约束

## 4.1 Functional Requirement

描述系统提供的行为。

例：

- 创建预约
- 查询预约
- 取消预约
- 修改排班

---

## 4.2 Non-functional Requirement

描述系统质量属性。

常见：

- 性能
- 可用性
- 可靠性
- 安全
- 可维护性
- 可观测性
- 兼容性
- 扩展性

坏：

> 系统应快速响应。

好：

> 在约定负载和数据规模下，预约查询接口 P95 响应时间不得超过 500ms。

---

## 4.3 Constraint

约束不是系统“做什么”，而是“必须在什么限制下做”。

例：

- 必须部署在客户内网
- 必须使用 SQL Server
- 必须支持 Chrome 最近两个主版本
- 数据必须保存在指定地区
- 必须兼容已有 HIS 接口

---

# 5. Business Rule 与 Requirement 的区别

业务规则是业务世界本身成立的规则。

例：

> 同一个号源在任何时刻最多只能有一个有效预约。

Requirement 是系统为了满足业务规则必须做的事。

例：

```
APPT-005
当多个请求同时尝试预约同一 Slot 时，系统必须确保最多只有一个请求成功。
```

一个 Business Rule 可能对应多个 Requirement。

---

# 6. Requirement 的质量属性

IREB 强调需求应具备质量。实际工作中可以使用以下清单。

## 6.1 Necessary 必要

问：

> 如果去掉它，业务目标是否仍能满足？

如果没有明确价值，可能是“想当然功能”。

---

## 6.2 Unambiguous 无歧义

坏：

> 系统应及时发送提醒。

“及时”是多少？

改：

> 预约开始前 24 小时，系统必须生成一条预约提醒任务。

---

## 6.3 Complete 完整

至少检查：

- Actor
- Trigger
- Preconditions
- Input
- Business Rule
- Expected Behavior
- Output
- Failure
- Boundary
- Postcondition

---

## 6.4 Atomic / Singular 单一

坏：

> 系统创建预约、发送短信、写日志并更新医生日程。

拆成：

- APPT-001 创建预约
- SLOT-002 占用号源
- NOTIF-001 生成通知任务
- AUD-001 写审计记录

---

## 6.5 Consistent 一致

不能出现：

```
R1: 患者可在预约前2小时取消。
R2: 所有预约只能由管理员取消。
```

---

## 6.6 Feasible 可实现

例如业务要求：

> “系统必须在任何情况下 100% 不宕机。”

从工程上不可实现，应进一步澄清服务目标、维护窗口、容灾等。

---

## 6.7 Verifiable 可验证

如果 QA 无法判断 PASS/FAIL，Requirement 通常还不够好。

坏：

> 页面设计应现代。

除非有明确设计规范，否则不可客观验证。

---

## 6.8 Traceable 可追踪

应能回答：

- 它来自哪里？
- 谁要求？
- 为什么需要？
- 影响哪些设计？
- 哪些测试验证它？

---

# 7. 固定句式降低歧义

推荐：

### 事件型

```
当 [Trigger] 时，系统必须 [Behavior]。
```

### 条件型

```
如果 [Condition]，系统必须 [Behavior]。
```

### 禁止型

```
系统不得 [Forbidden Behavior]。
```

### 能力型

```
系统必须允许 [Actor] [Action]。
```

不要机械套模板，而是利用结构帮助自己发现缺项。

---

# 8. Requirement ID

建议稳定编号：

```
AUTH-001
PAT-001
DOC-001
SLOT-001
APPT-001
NFR-PERF-001
NFR-SEC-001
```

ID 最重要的作用：
- 追踪
- 讨论
- 版本变更
- 测试引用
- 缺陷引用

不要因为 Requirement 标题改了就换 ID。

---

# 9. Requirement Attribute

成熟项目不会只存“正文”。

建议至少维护：

| 属性 | 示例 |
|---|---|
| ID | APPT-001 |
| Title | 创建预约 |
| Type | Functional |
| Source | Patient Workshop |
| Rationale | 减少电话预约 |
| Priority | Must |
| Status | Approved |
| Owner | Product |
| Version | 1.2 |
| Verification | API + E2E |
| Related Rule | BR-003 |
| Related Use Case | UC-APPT-01 |
| Related Test | TC-APPT-001 |

这也是 IBM DOORS、Polarion、Codebeamer 等需求管理工具背后的基本思想。

---

# 10. Priority：MoSCoW

常见优先级方法：

- Must have
- Should have
- Could have
- Won't have now

注意：

“Must”不是“我很喜欢”。

Must 应满足：

> 如果没有这项，本次交付是否无法实现核心目标、合规或关键运营？

---

# 11. Requirement Lifecycle

可以定义：

```
Draft
 ↓
In Review
 ↓
Approved
 ↓
Implemented
 ↓
Verified
```

也可能出现：

```
Rejected
Deferred
Obsolete
Changed
```

不要只有“完成/未完成”。

---

# 12. Baseline

IREB Glossary 中 Baseline 指一个稳定、受变更控制的工作产品配置。

工程上理解：

> “这一版已经批准，可以作为开发和测试依据。”

形成基线后，修改不能悄悄发生。

可用：
- Git tag
- 文档版本
- Requirements Management Tool 的 baseline

---

# 13. Change Management

需求一定会变。

一个合格 Change Request 至少回答：

1. 为什么改？
2. 原行为？
3. 新行为？
4. 影响哪些 Requirement？
5. API？
6. Data？
7. UI？
8. Security？
9. Test？
10. Documentation？
11. Release？
12. 风险？
13. 谁批准？

---

# 14. Traceability

建立：

```
Business Goal
  ↓
Requirement
  ↓
Design / API / Data
  ↓
Development Task
  ↓
Test Case
  ↓
Test Result
```

### Forward Traceability

Requirement → Implementation/Test

回答：

> 这个 Requirement 被实现和验证了吗？

### Backward Traceability

Test/Feature → Requirement

回答：

> 为什么系统里有这个功能？

---

# 15. 一个完整改写案例

原始需求：

> “用户可以修改个人资料。”

问题：

- 哪类用户？
- 哪些字段？
- 哪些字段不可改？
- 是否需要身份验证？
- 是否影响其他系统？
- 是否审计？
- 是否立即生效？
- Email 修改是否验证？
- 手机修改是否 OTP？
- 并发修改怎么办？

候选拆分：

```
PROFILE-001
已认证用户必须能够查看自己的个人资料。

PROFILE-002
用户必须能够修改 displayName。

PROFILE-003
用户不得直接修改系统内部 userId。

PROFILE-004
修改手机号前，系统必须完成新手机号验证。

PROFILE-005
修改成功后，系统必须记录审计事件。
```

然后继续关联：
- API
- Schema
- Permission
- Test Case

# 16. 常见反模式

## 16.1 页面即需求

> “页面放三个按钮。”

先问：
- 用户目标是什么？
- 按钮分别触发什么业务行为？

## 16.2 解决方案当需求

> “必须用 Redis。”

这是技术约束或设计决定，除非有明确来源，不应伪装成业务 Requirement。

## 16.3 把会议纪要当 Spec

会议纪要记录“讨论发生了什么”，但正式 Spec 需要整理成：
- Fact
- Decision
- Requirement
- Open Question

## 16.4 大段自然语言

一页大段文字很难：
- 追踪
- 测试
- 版本比较

应拆成有 ID 的原子需求。

# 17. 本章练习

原始描述：

> “患者可以方便地预约喜欢的医生。如果号满了要提示。管理员可以管理预约。系统要安全稳定。”

请完成：

1. 识别至少 4 个模糊词。
2. 写 3 条 Business Requirement。
3. 写 5 条 User Requirement。
4. 写 12 条 System Requirement。
5. 写 3 条 NFR。
6. 写 3 条 Constraint。
7. 每条分配 ID。
8. 每条填写 Source、Priority、Verification。
9. 写出至少 5 个 Open Question。
10. 建一个 Traceability 表。

---

# 18. 自测题

1. Requirement 和 Business Rule 有什么区别？
2. 为什么“支持批量导出”不是天然的好 Requirement？
3. 什么是可验证？
4. Baseline 与普通文档版本有什么区别？
5. 为什么 Requirement 要有唯一 ID？
6. 正向追踪和反向追踪分别解决什么问题？
7. 什么情况下应该拆 Requirement？
8. “必须使用 PostgreSQL”属于哪类信息？
9. 如果 Product 和 QA 对同一条 Requirement 理解不同，意味着什么？
10. Open Question 为什么不能隐藏在聊天记录里？

---

# 19. 本章完成标准

你看到一句：

> “做一个用户登录功能。”

能够主动拆出：
- 业务目标
- Actor
- Success
- Failure
- Security
- Rate Limit
- Error
- Audit
- Session
- Test
- Open Questions

而不是直接交给开发。
