# 10 非功能需求：安全、性能、可靠性与可观测性

## 本章目标

新手最容易只写功能。商业软件的质量往往由 NFR 决定。

## 一、NFR 常见类别

- 性能 Performance
- 可用性 Availability
- 可靠性 Reliability
- 可扩展性 Scalability
- 安全 Security
- 隐私 Privacy
- 可维护性 Maintainability
- 可观测性 Observability
- 兼容性 Compatibility
- 可访问性 Accessibility
- 数据保留
- 审计

## 二、性能必须量化

坏：
> 页面要快速加载。

好：
> 在正常负载下，95% 的预约列表 API 响应时间必须低于 500 ms。

还应定义：
- 测量位置
- 数据量
- 并发量
- 百分位
- 排除条件

## 三、可用性

例：
> 核心预约服务月可用性目标为 99.9%。

还需要：
- 计划维护是否计算
- 监测方式
- 故障恢复目标

## 四、RTO / RPO

RTO：发生灾难后允许多久恢复。

RPO：最多允许丢失多长时间的数据。

它们属于业务与架构共同决定的规格。

## 五、认证与授权

Authentication：
“你是谁？”

Authorization：
“你能做什么？”

Spec 必须清晰区分。

## 六、权限矩阵

| 功能 | 患者 | 医生 | 前台 | 管理员 |
|---|---|---|---|---|
| 查看自己的预约 | √ | - | √ | √ |
| 查看全部患者预约 | - | - | 条件允许 | √ |
| 修改排班 | - | 自己 | - | √ |

矩阵之后还要补充对象级权限，例如“只能访问自己的记录”。

## 七、OWASP 思维

API 尤其关注：
- 对象级授权
- 身份认证
- 属性级授权
- 资源消耗
- 敏感业务流程
- 配置错误
- 第三方 API 风险

不要把“安全”只写成“使用 HTTPS”。

## 八、审计

关键操作至少考虑：
- 谁
- 何时
- 对什么对象
- 做了什么
- 原值
- 新值
- 来源 IP / Client（视场景）
- 结果

审计日志与普通调试日志不同。

## 九、可观测性

Spec 可以定义：
- 必须记录哪些业务事件
- 指标
- 告警
- Trace ID / Correlation ID
- 错误分类

例如：
> 每个外部 API 请求必须携带可追踪的 correlation ID。

## 十、练习

为预约系统写：
- 3 条性能需求
- 2 条可用性需求
- 5 条安全需求
- 3 条审计需求
- 2 条可观测性需求

每条必须可验证。
