# 10 非功能需求：安全、性能、可靠性、可观测性

> 本章目标：学会把“系统要安全、稳定、快速”转换为可以设计和验证的质量属性 Requirement。

## 1. NFR 为什么重要

系统功能全部正确，也可能不能商用：

- 太慢
- 经常宕机
- 数据泄露
- 无法恢复
- 无监控
- 无审计
- 高并发崩溃

因此 NFR 会直接影响架构。

Microsoft Azure Well-Architected Framework 重点关注：
- Reliability
- Security
- Cost Optimization
- Operational Excellence
- Performance Efficiency

## 2. 功能 vs 非功能

功能：

> 系统允许创建预约。

NFR：

> 在正常业务负载下，创建预约 API 的 P95 响应时间不得超过 X ms。

## 3. NFR 必须可测量

坏：

> 系统必须高性能。

好：

```
PERF-001
在 500 并发用户、数据库包含 100 万条历史 Appointment 的指定测试环境下，
GET /appointments 的 P95 响应时间不得超过 500 ms。
```

参数必须来自真实业务和容量规划，不要照抄案例数字。

## 4. Latency

不要只写 Average。

常见：
- P50
- P95
- P99

原因：

如果平均 100ms，但 5% 用户要 5 秒，平均值仍然可能“好看”。

## 5. Throughput

例如：

> 系统每秒需要处理多少请求？

可用：
- RPS
- jobs/minute
- messages/sec

## 6. Capacity

定义：
- concurrent users
- total users
- data volume
- storage growth

没有容量上下文，性能指标很难解释。

## 7. Availability

例：

> 核心预约服务月度可用性目标为 99.9%。

还必须定义：
- measurement
- planned maintenance
- excluded events
- endpoint scope

## 8. Reliability

Reliability 不只是“在线”。

还包括：
- failure handling
- recovery
- data consistency
- redundancy
- backup
- disaster recovery

## 9. RTO / RPO

### RTO
最多允许多久恢复。

### RPO
最多允许丢失多长时间的数据。

例如：
- RTO 2h
- RPO 15min

数字必须由业务风险决定。

## 10. Scalability

问：
- 用户增长 10 倍怎么办？
- 数据增长 10 倍怎么办？
- 峰值是否季节性？
- 是否需要水平扩展？

Spec 应描述容量目标，而不是擅自指定某个云服务。

## 11. Authentication

回答：

> 你是谁？

包括：
- login
- MFA
- session
- token
- password reset
- lockout

## 12. Authorization

回答：

> 你能做什么？

必须考虑：
- Role
- Object Ownership
- Tenant
- State
- Context

例：

即使 Patient 拥有 PATIENT 角色，也不能读取其他患者的 Appointment。

## 13. OWASP API Security

OWASP API Security Top 10 重点包括：
- Broken Object Level Authorization
- Broken Authentication
- Broken Object Property Level Authorization
- Unrestricted Resource Consumption
- Sensitive Business Flow abuse
- Security Misconfiguration
- Unsafe Consumption of APIs

对 Spec Engineer 最重要：

> 权限不是“页面有没有按钮”，而是服务端是否验证每个对象和操作。

## 14. Sensitive Data

NFR 应考虑：
- transit encryption
- storage protection
- masking
- logging restriction
- access control
- retention

不要把“用了 HTTPS”当成全部安全要求。

## 15. Audit

关键业务应考虑：

```
who
when
what
object
before
after
result
source
correlation
```

审计日志需要保护，不应被普通用户随意删除。

## 16. Observability

三个常见支柱：

- Logs
- Metrics
- Traces

Spec 可以定义：

> 每个外部请求必须产生 correlation ID。

> Appointment 创建失败应产生可监控指标。

## 17. Logging

不要记录：
- password
- full token
- secret
- unnecessary sensitive data

错误日志要有足够上下文，但不能泄密。

## 18. Alerting

“有日志”不等于“可运维”。

需要考虑：
- error rate
- queue backlog
- dependency failure
- latency spike
- authentication abuse

## 19. Maintainability

可包括：
- API documentation
- coding standards
- automated tests
- modularity
- upgrade strategy

这类 NFR 通常由工程组织共同定义。

## 20. Accessibility

面向公众的软件可能有可访问性要求。

可参考 WCAG。

例如：
- keyboard navigation
- contrast
- screen reader
- form labels

## 21. Compatibility

定义：
- Browser
- OS
- Device
- API version
- External system version

不要写：

> 支持所有浏览器。

## 22. Backup / Restore

Spec 要问：
- backup frequency
- retention
- encryption
- restore test
- RPO
- RTO

只有备份、没有恢复演练，不等于可靠。

## 23. NFR 模板

```
ID:
Quality Attribute:
Scenario:
Environment:
Stimulus:
Response:
Measure:
Verification:
```

示例：

```
ID: PERF-001
Attribute: Performance
Scenario: Patient lists appointments
Environment: normal production-equivalent load
Stimulus: GET /appointments
Response: return authorized appointment list
Measure: P95 <= 500ms
Verification: load test
```

## 24. NFR 与架构

NFR 会驱动设计：

- 高可用 → redundancy
- 低延迟 → cache/index
- 高吞吐 → async/scaling
- 强一致 → transaction
- 灾备 → backup/replication

所以 NFR 不能开发结束后才补。

## 25. 练习

为医疗预约写：

- 5 Performance
- 3 Reliability
- 3 Availability
- 5 Security
- 3 Privacy
- 3 Audit
- 3 Observability
- 2 Compatibility
- 2 DR

每条必须包含：
- condition
- measurable target
- verification

## 26. 自测

1. 为什么平均响应时间不够？
2. RTO/RPO 区别？
3. Authentication/Authorization 区别？
4. 为什么对象级权限重要？
5. Audit 与 Log 区别？
6. Observability 包括哪些？
7. NFR 为什么影响架构？
8. 为什么“支持所有浏览器”是坏需求？
