# 15 Spec Engineer 能力评估、作品集与面试

## 1. 学完仓库后，不以“看完”为标准

真正的完成标准是你可以面对一个模糊业务需求，独立完成：

```
业务目标
→ Stakeholder
→ Scope
→ Elicitation
→ Business Rules
→ Functional Requirements
→ Models
→ API/Data Spec
→ NFR
→ Acceptance Criteria
→ Test Design
→ Traceability
→ Change Management
```

---

## 2. 初级能力矩阵

### 软件基础
- 理解前端/后端/数据库
- 理解 HTTP

- 理解 Git

### 测试

- 边界值

达到这些，可以参与团队需求工作。

## 6. 面试高频：什么是好的 Requirement？

回答不要只背“清晰完整”。

可以说：

一个高质量 Requirement 应该：
- 必要
- 单一
- 明确
- 一致
- 可实现
- 可验证
- 可追踪
- 处于正确抽象层级

然后给一个改写案例。

---

## 7. 面试题：需求很模糊怎么办？

回答结构：

1. 不直接猜。
2. 确认业务目标。
3. 找 Stakeholder。
4. 分离事实和假设。
5. 用 Example / Prototype / Model 澄清。
6. 记录 Open Questions。
7. 形成候选 Requirement。
8. 与 Product/Dev/QA 验证。
9. 形成批准版本。

---

## 8. 面试题：Product 和 Developer 理解不一致怎么办？

不要回答“开会沟通”。

更好的步骤：
- 定位冲突具体在哪句话
- 对照 Business Goal / Rule
- 给出不同解释对应的系统行为
- 用场景或例子验证
- 明确决策人
- 记录 Decision
- 更新 Spec
- 更新测试

---

## 9. 面试题：如何判断需求可测试？

问：
- 前置条件是否明确？
- 输入是否明确？
- 行为是否明确？
- 输出是否明确？
- 边界是否明确？
- 是否有量化标准？
- 能否明确判断 PASS/FAIL？

“系统应该响应快”不可测试。

“在 X 并发和 Y 数据量下，P95 ≤ 500ms”可测试得多。

---

## 10. 面试题：API Spec 要包含什么？

至少：
- method
- path
- purpose
- auth
- params
- request body
- schema
- validation
- success
- errors
- examples
- idempotency
- pagination/filter
- versioning
- audit/security（按场景）

---

## 11. 面试题：遇到需求变更怎么办？

结构化回答：

```
Change Request
→ Why
→ Diff
→ Impact Analysis
→ Estimate/Risk
→ Decision
→ Update Spec
→ Update Traceability
→ Update Dev/Test
→ New Baseline
```

## 12. 面试案例题

题目：

> “做一个忘记密码功能。”

你应该主动询问：

### 用户
- 哪些账号支持？
- 未注册用户如何提示？

### 验证
- 邮件？
- 手机？
- 管理员？
- MFA？

### Token
- 有效期？
- 一次性？
- 使用后失效？
- 重发后旧 Token 是否失效？

### 安全
- 是否泄露账号存在？
- Rate Limit？
- 暴力请求？
- Audit？

### 密码
- 强度
- 是否允许最近密码
- 修改后旧 Session 是否失效

### 异常
- 邮件发送失败
- Token 过期
- Token 已用
- 重复提交

这比直接画“忘记密码页面”更体现 Spec 能力。

## 13. 综合自测项目

不看本仓库答案，从零设计：

**企业员工请假 SaaS**

要求至少包括：
- 员工
- 主管
- HR
- Admin

功能：
- 提交请假
- 审批
- 撤回
- 拒绝
- 余额
- 历史查询

必须提交：
- Scope
- Stakeholder
- Glossary
- Business Rule
- 20+ Requirements
- Flow
- State
- Sequence
- API
- Data Model
- Permission Matrix
- NFR
- 15+ Acceptance Criteria
- 30+ Test Cases
- Traceability
- Change Request

完成后再和医疗预约案例对照。

## 最终毕业标准

当你能够接到一句：

> “我们想做一个 SaaS，让用户可以预约。”

然后不急着写页面、不急着写代码，而能系统地把它转化为：

**Scope → Model → Rules → Requirements → Contract → Quality → Tests → Traceability**

你已经具备 Spec Engineer 的核心工作方式。
