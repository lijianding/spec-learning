# 07 系统设计与架构基础

## 本章目标

Spec Engineer 不必成为架构师，但必须理解常见架构元素，否则很难写出可实现、可验证的技术规格。

## 一、先理解系统边界

任何 Spec 都要先回答：

- 哪些能力属于本系统？
- 哪些由外部系统提供？
- 数据从哪里进入？
- 数据到哪里去？
- 哪些接口由我们负责？
- 哪些依赖第三方？

## 二、常见组件

### 前端
浏览器、Web App、移动端等。

### 后端
承载业务规则、权限、事务、接口。

### 数据库
保存结构化数据。

### 缓存
提升读取速度、减少数据库压力。

### 消息队列
用于异步处理、解耦和削峰。

### 对象存储
保存文件、图片等。

### 第三方服务
短信、邮件、支付、地图、身份认证等。

## 三、C4 思维

C4 常用于表达：

- System Context：系统和外部环境
- Container：Web、API、数据库等主要容器
- Component：容器内部组件
- Code：必要时进一步展开

Spec Engineer 通常重点看前两层。

## 四、同步与异步

同步：
- 用户请求后等待结果
- 适合需要立即反馈

异步：
- 请求提交后先返回
- 后台继续处理

例：预约创建成功后发送短信，可以设计为异步，避免短信服务慢导致主交易失败。

Spec 中要明确：
- 谁负责重试？
- 最多重试几次？
- 最终失败如何记录？
- 是否影响主业务？

## 五、事务与一致性

涉及多个数据修改时要思考：
- 是否必须同时成功？
- 部分失败怎么办？
- 是否允许最终一致？

例如创建预约：
1. 占用号源
2. 创建预约记录
3. 写审计日志
4. 发送通知

前三者可能需要强一致，而通知通常可以异步。

## 六、并发

预约场景最典型：

两名用户同时预订最后一个号源。

Spec 不能只写“检查可用再创建”，因为两个请求可能同时检查到 AVAILABLE。

需要定义业务保证：
> 同一号源在任何时刻最多只能存在一个有效预约。

实现方式由架构/开发选择，但 Spec 应明确不变量和失败行为。

## 七、依赖关系

每个外部依赖至少记录：
- 系统名称
- 接口
- SLA
- 超时
- 重试
- 失败降级
- 数据责任
- 安全方式

## 八、练习

为医疗预约 SaaS 画一张 System Context 和 Container 图，并标出：
- Web
- API
- DB
- 短信服务
- 身份认证服务

再写 5 个外部依赖风险。
